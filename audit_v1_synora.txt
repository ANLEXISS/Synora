## 1. Résumé exécutif

Le dépôt contient une base technique réelle : services Go séparés, API REST, WebSocket, bus Unix, StateStore atomique, authentification par session, WebApp React, worker Python, association de caméras Synora et healthcheck de boot.

Il ne constitue pas une V1 vendable.

Les parcours critiques cassent principalement pour les raisons suivantes :

1. Aucun véritable modèle d'incident n'existe.
2. Les références faciales enregistrées par l'API ne sont pas consommées par le Vision Worker.
3. Le suivi runtime des tracks, inconnus, clusters et fenêtres n'est pas câblé dans Core.
4. L'OTA signée et le rollback ne sont pas implémentés.
5. Les contrôles de sécurité opérationnels sont insuffisants : bus injectable localement, HTTPS optionnel, bootstrap administrateur non consommé.

Conclusion : NON VENDABLE EN L'ÉTAT.

### Points forts

- Séparation claire bus -> core -> API -> WebApp.
- Sessions basées sur des tokens aléatoires hashés et persistés.
- Bcrypt pour les mots de passe.
- Écritures atomiques du StateStore et des configurations.
- Authentification caméra HMAC avec fenêtre temporelle.
- Timeout caméra de 30 secondes.
- API de pairing Synora Camera réellement présente.
- Healthcheck de boot avec rapport JSON atomique.
- Nombreux tests unitaires et tests de contrats.

### Cinq blocages majeurs

1. BLOCKER : incidents absents — pas de modèle, persistance, route, acquittement ou notification.
2. BLOCKER : références faciales découplées du Vision Worker — chemins différents et rebuild déclaratif.
3. BLOCKER : OTA/rollback absents — RAUC seulement documenté, rollback runtime explicitement désactivé.
4. CRITICAL : tracking des résidents et inconnus non alimenté par le chemin runtime réel.
5. CRITICAL : sécurité opérationnelle insuffisante — bus local injectable, HTTPS non obligatoire, bootstrap non consommé.

## 2. Architecture réellement observée

### Services

- synora-bus : bus JSON newline sur /run/synora/bus.sock.
- synora-core : ingestion des événements, moteur de décision et StateStore.
- synora-api : REST, WebSocket, authentification et WebApp statique.
- synora-discovery : ingress clips, runtime caméra, queue Vision et supervision du worker.
- Vision Worker Python : décodage, détection, tracking et reconnaissance.
- synora-actions : exécution d'actions et notifications.
- synora-connect : connectivité distante.
- synora-runtime-manager : santé et snapshots runtime.
- MediaMTX : flux média, dépendance externe.
- synora-web : application React/Vite.

Les unités systemd configurent des redémarrages automatiques, mais synora-discovery s'exécute en root et aucune unité n'intègre réellement RAUC ou mark-good.

### Communications et stockage

Le flux implémenté est :

    Caméra Synora
      -> POST multipart /vision + HMAC
      -> synora-discovery :7070
      -> fichier clip temporaire puis renommage
      -> queue mémoire de clips
      -> /run/synora/vision-worker.sock
      -> Vision Worker Python
      -> bus Unix, Source=discovery, Target=core
      -> synora-core
      -> StateStore
      -> API /api/state
      -> WebSocket /api/ws
      -> WebApp

Preuves principales :

- Routes API : cmd/synora-api/main.go:163-245.
- Ingress : internal/discovery/ingress/server.go:88-282.
- Requête Vision : internal/discovery/vision/runtime.go:28-56 et 174-223.
- Publication Vision : internal/discovery/vision/worker.go:24-105.
- Bus : internal/bus/server.go:29-49 et 95-151.
- StateStore : internal/state/store.go:13-35.

Le flux casse avant le résultat V1 complet :

- les métadonnées de séquence ne sont pas transportées dans vision.Request ;
- la file est volatile ;
- le socket Vision n'a pas de deadline de lecture ;
- les erreurs de publication sont journalisées puis ignorées ;
- Core ne crée pas d'incident ;
- la WebApp n'a pas de vue incident.

### Divergences avec l'architecture annoncée

- L'architecture produit suppose des incidents ; aucun composant incident n'existe.
- Elle suppose un suivi multi-pièces ; les structures existent mais ne sont pas alimentées par le runtime.
- Elle suppose une OTA fiable ; le dépôt ne contient qu'un healthcheck et des contrats préparatoires.
- Elle est caméra Synora uniquement ; l'API et l'UI exposent encore plusieurs types de périphériques et automations générales.

## 4. Parcours de bout en bout

### Première installation

Étapes existantes : synora-bootstrap-config init --apply, génération token/session/PSK/mot de passe, écriture des YAML puis démarrage des services.

Point de rupture : aucun onboarding Web ni état first-run. L'utilisateur ne peut pas terminer proprement réseau, caméra, pièce, topologie, résident, visage et validation finale.

Données : configuration potentiellement partiellement écrite, mais aucune progression persistée.

Tests nécessaires : système vierge, interruption à chaque étape, reprise et bootstrap répété.

### Résident reconnu

Le parcours attendu est : résident -> photos -> rebuild -> chargement worker -> embedding -> identité -> présence.

Rupture confirmée : API /var/lib/synora/vision/face, worker /opt/synora/services/vision-worker/data/faces. Preuves : configs/security.yaml:16-18, deployments/systemd/synora-api.service:12-16 et services/vision-worker/modules/face/FaceRecognizer.py:15-23.

Le rebuild ne produit pas d'embeddings et ne recharge pas le worker : cmd/synora-api/face_handlers.go:156-175.

### Inconnu détecté

vision.unknown peut être généré et le moteur peut passer à suspicious dans les tests synthétiques.

Le parcours casse ensuite : aucun anonymous/entity track durable, aucun suivi inter-caméras, aucun incident, aucune notification et aucune preuve conservée comme incident.

### Caméra déconnectée

Le runtime marque la caméra offline après 30 secondes sans clip et la remet online au prochain clip.

Manques : persistance du runtime registry, notification utilisateur, incident caméra offline, test réel de coupure/reconnexion et traitement de file pendant indisponibilité.

### Incident et acquittement

Parcours impossible. Aucun modèle Incident, endpoint, RPC, stockage, UI ou notification. /api/intrusion/reset modifie l'état système mais ne crée ni ne conserve une preuve structurée.

### Redémarrage sans perte

Préservé : configurations YAML, utilisateurs, sessions, StateStore JSON, résidents, topology, métadonnées limitées d'événements, danger et action results bornés.

Perdu ou réinitialisé : queue clip, queue bus non durable, runtime camera registry, pairing pending, connexion Vision, tracks runtime, embeddings en mémoire, progression onboarding et statuts notification inexistants.

Risque : StateStore peut redémarrer avec métadonnées mais sans correspondance physique des clips.

### OTA et rollback

Le dépôt sait lire une version, produire un healthcheck et écrire un rapport atomique. Il ne sait pas vérifier un bundle signé, sélectionner un slot, installer, compter les boots, appeler mark-good ou effectuer un rollback.

- Cause : absence de contrat synchronisation/reload.
- Conséquence : reconnaissance résident non démontrée.
- Correction : racine commune configurable, embeddings versionnés, reload atomique.
- Non-régression : ajout photo -> rebuild -> reload -> clip réel -> identity.

### AUDIT-003 — CRITICAL — Tracks runtime absents

- Attendu : résident/inconnu suivi entre pièces.
- Actuel : Track, Cluster et EventWindow existent mais SetTrack, SetCluster et SetEventWindow ne sont pas appelés par le runtime Vision.
- Conséquence : pas de trajectoire multi-caméra.
- Correction : propriétaire Core unique des tracks et corrélation track_id/sequence_key.
- Non-régression : caméra A -> caméra B avec événements retardés et doublons.

### AUDIT-004 — CRITICAL — Erreurs de publication Vision perdues

- Attendu : retry, dead-letter ou échec visible.
- Actuel : internal/discovery/vision/worker.go:54-105 journalise, continue puis retourne nil.
- Conséquence : clip traité avec état Core incomplet.
- Correction : résultat par clip, retry borné, statut durable.
- Non-régression : bus indisponible pendant publication.

### AUDIT-005 — CRITICAL — Timeout Vision non appliqué

- Attendu : clip bloqué libère worker et produit une erreur.

### AUDIT-006 — CRITICAL — Bus local injectable

### AUDIT-007 — HIGH — Clips sans idempotence, validation complète ni rétention disque

## 6. Sécurité

### Vulnérabilités confirmées

- Injection d'événements par producteur bus local non authentifié.
- HTTPS restant disponible en clair si TLS absent.
- Rejeu possible d'une requête caméra signée dans la fenêtre de 30 secondes, faute de nonce/cache.
- Debug facial et images runtime écrits sans politique de rétention claire.
- Worker Vision sur socket Unix sans authentification dédiée.
- Discovery exécuté en root.

### Risques plausibles nécessitant validation

- CheckOrigin=true sur WebSocket avec session cookie.
- Exposition de noms de clips via permissions de répertoire.
- Usurpation caméra avec MAC/setup token si clé publique désactivée.
- Saturation disque clips/debug.
- Désynchronisation après suppression résident/caméra.

### Protections présentes

- Bcrypt.
- Cookies HttpOnly/SameSite=Strict.
- Hash des sessions.
- Rotation/révocation sessions.
- Limite login.
- Validation chemins photos.
- Limites uploads.
- HMAC caméra.
- Sanitization snapshots.
- Permissions prévues sur configurations.

### Blocages absolus avant commercialisation

Incident lifecycle, TLS obligatoire, authentification producteurs bus, bootstrap admin consommable, reconnaissance faciale raccordée, OTA/rollback et politique clips/biométrie.

## 7. Persistance et résistance aux pannes

### Données persistées

- Configurations YAML.
- Résidents et topology.
- Authentification.
- Sessions.
- StateStore JSON.
- Identités et présence selon TTL.
- Métadonnées clips.
- Danger assessments bornés.
- Action results bornés.
- Événements récents bornés.
- Event chains.

### Données perdues au redémarrage

- Queue clip.
- Queue bus non durable.
- Runtime camera registry.
- Pairing pending.
- Connexion Vision.
- Tracks non alimentés.
- Embeddings chargés en mémoire.
- Progression onboarding.
- Statuts notification inexistants.

### Écritures et corruption

Le StateStore utilise temp + Sync + Rename + synchronisation du répertoire.

Limites :

- tous les setters runtime ne déclenchent pas eux-mêmes SaveNow ;
- la cohérence dépend du chemin appelant ;
- pas de WAL ;
- corruption -> renommage du fichier et état vide ;
- pas de restauration automatique depuis backup ;
- migrations configuration no-op et non branchées.

### Rétention

- recent events : 200.
- danger : 100.
- action results : 200.
- présence/tracks/clips par expiration.
- fichiers clip physiques : aucune purge confirmée.
- photos archivées/crops : aucune rétention confirmée.
- logs/debug : aucune rotation confirmée.

## 8. Contrats à figer avant l'UI/UX

### Authentification

Réutiliser POST /api/auth/login, POST /api/auth/refresh, POST /api/auth/logout et GET /api/auth/me.

Contrat minimal :

    {
      "session": { "expires_at": "timestamp", "refreshable": true },
      "user": { "id": "user_id", "role": "admin|resident|guest", "permissions": [] }
    }

Ajouter bootstrap initial, changement obligatoire et révocation globale.

### Caméras

Réutiliser pairing Synora Camera et GET/PATCH/DELETE /api/devices/{id}.

Contrat minimal :

    {
      "id": "cam_01",
      "serial": "...",
      "model": "...",
      "room_id": "room_entry",
      "status": "online|offline|pairing|disabled",
      "last_seen": "...",
      "capabilities": ["clip", "live"],
      "trust": { "key_id": "...", "paired_at": "..." }
    }

### Résidents

Réutiliser CRUD résident et routes face. Ajouter face_profile.status, reference_count, dataset_version, embedding_status, last_rebuilt_at et delete_policy.

### Topologie

    {
      "rooms": [
        { "id": "room_entry", "name": "Entrée", "floor": 0, "neighbors": ["room_hall"] }

    }

La topologie doit être une dépendance explicite du tracking.

### Événements

pkg/contract/event.go:87-114 contient déjà activation_id, clip_id, clip_index, track_id et sequence_key.

Ils doivent être obligatoires pour les événements Vision, avec occurred_at, received_at, camera_id, room_id, identity et confidence.

### Incidents

Nouveau contrat obligatoire :

    {
      "id": "inc_...",

      "room_id": "room_entry",
      "identity": null,
      "event_ids": [],

      "timeline": [],

    }

### Clips

Ajouter hash, taille, durée, MIME, chemin interne non exposé, expiration, statut received/queued/processing/processed/failed et idempotency key.

### État système

Réutiliser PublicSnapshot et SystemState. Ajouter state_revision, last_incident_id, active_incident_count, degraded_reasons, camera_summary et vision_worker_status.

### WebSocket

    {
      "version": 1,
      "type": "snapshot|event|incident.updated|system.updated",
      "revision": 42,
      "sequence": 1002,
      "occurred_at": "...",
      "payload": {}
    }

Ajouter abonnement, heartbeat, replay depuis sequence et réponse de resynchronisation.

### Erreurs API

Le format existant est réutilisable :

    { "error": "validation_failed", "message": "Room does not exist", "details": {} }

Documenter les codes HTTP, limites, pagination et erreurs de permission.

8. Reboot sans perte.
9. Quota/rétention clips.
10. TLS et sécurité bus.
11. Tests longue durée et coupure réseau.

### Avant la vente

1. OTA signée.
2. Rollback automatique vérifié.
3. Bootstrap admin sécurisé.
4. Protection dernier administrateur.
5. Incident et notification fiables.
6. Backup/restauration.
7. Export diagnostic sans secrets.
8. Suite Go complète verte.
9. Build Web reproductible.
10. Documentation alignée avec le code.
11. Validation hardware de toutes les promesses commerciales.

### Fonctionnalités à désactiver ou masquer immédiatement

- Automations domotiques générales.
- Périphériques tiers.
- CGE/Lab/validation admin.
- Simulation.
- Détection arme, chute et bagarre.
- Toute promesse de suivi multi-pièces tant que les tracks runtime ne sont pas câblés.
- Toute présentation d'un simple événement comme un incident.
- OTA/rollback tant que RAUC n'est pas opérationnel.
- Accès HTTP non sécurisé en production.

### Décisions nécessitant validation humaine

- Politique exacte d'intrusion pour un inconnu.
- Seuils et délais suspicious/intrusion.

- Niveau de confiance requis pour reconnaître un résident.
- Date à laquelle les fonctions Vision expérimentales pourront devenir des promesses commerciales.

Verdict : la base logicielle est un prototype avancé et un laboratoire d'intégration, mais Synora Founders Edition n'est pas vendable en l'état.
